# Phase-by-phase implementation plan (a0–a4)

**Ground rule:** the iOS app (`../../ios-study-wrapper/ios-study-wrapper/`)
is the reference implementation and the extension repo's
`docs/config-schema.md` is the normative contract. Every section below names
what is *ported* (behavior identical, code translated) vs what is *adapted*
(Android platform necessity, difference recorded in §6). When in doubt, open
the named iOS file and translate it — do not redesign.

Milestone checklist with acceptance criteria: §5. Platform-difference ledger:
§6.

## Phase a0 — scope decisions & contract reuse

Everything the extension/iOS contracts already settle is **inherited, not
reopened**: config schema §1–§5, code normalization, origin match rule,
target-action semantics, enroll idempotency (409 = success), kill-switch
posture, one-study-per-install, consent-before-enroll ordering.

### a0.1 Scope

Same three-screen scope as iOS v1 (activation → consent → browser), plus the
study-home and ended-study states. Non-goals as listed in
[README.md](README.md). Browser starts at the first origin at
`flow.prepositionPath` when configured, else its root.

### a0.2 Enroll client marker — **needs backend sign-off before a2 enroll work**

Mirror the iOS i0.2 decision (locked 2026-08-14) with Android values: the
enroll body carries BOTH `client: "android"` and
`extensionVersion: "android/<versionName>"`. The backend already accepts the
iOS split; this is the same shape with a new value — confirm with the backend
owner that `"android"` is admitted (and billed/segmented) before enrolling
real participants. Change only in `Constants.kt`.

### a0.3 Injection strategy (the decision that replaces iOS's i0.3)

- **Primary:** `WebViewCompat.addDocumentStartJavaScript(webView, script,
  allowedOriginRules)` — document-start, all matching frames, origin-scoped
  by the platform.
- `allowedOriginRules` derived from `tracking.origins` in one place next to
  `Origins.kt`: each origin `O` → `https://O` **and** `https://*.O` (the
  wildcard rule does not cover the bare domain — both are required to equal
  the §5 match rule).
- **The injected JS origin guard stays** (same as iOS ScriptBuilder): layer 2
  defense, protects against rule-derivation bugs, and keeps script assembly
  byte-comparable across platforms. The native navigation policy (§a2.5) is
  layer 3, the scope-keeper for top-level navigation.
- **No fallback injection path.** If
  `WebViewFeature.isFeatureSupported(DOCUMENT_START_SCRIPT)` (or
  `WEB_MESSAGE_LISTENER`) is false, the app shows a blocking "update Android
  System WebView" screen linking to the WebView Play Store page.
  `evaluateJavascript`-at-`onPageStarted` injection is racy (misses the tag's
  synchronous early events) and would silently produce non-parity data —
  worse than refusing. Both features have shipped in WebView for years;
  the gate is a safety net, not an expected path.

### a0.4 Participant identity & backup

iOS uses the Keychain so `participantId` survives reinstall. Android
analogue: store `p_<uuid>` in SharedPreferences **included in Auto
Backup/device-transfer rules** — best-effort reinstall survival. A fresh
device (or backup off) mints a new participant; that is already accepted in
the billing definition (same posture as desktop and the iOS keychain-
unavailable fallback). Do not add Google sign-in or server-side identity for
this. All other state (activeStudy, consent, endedStudy, ownTagHosts) also
lives in SharedPreferences via the `KeyValueStore` SPI.

### a0.5 Consent wording & version

Port the iOS `ConsentView` wording verbatim (it is already device-appropriate:
"this app", in-app browser explanation, what-is-collected bullets, random
participant ID). `ConsentConstants.textVersion = "android-<yyyy-MM-dd>"` —
the `android-` prefix keeps it distinct from `ios-*` and extension versions
because the audit reference must identify one exact displayed text. **Any**
visible wording change bumps the date. Enrollment sends this version; the
server stores it as the GDPR audit record.

### a0.6 Minimums

minSdk 26, portrait-locked, phones. Kotlin + Compose + single activity +
ViewModel. AndroidX WebKit, Browser (Custom Tabs), Lifecycle-process.
Two build types only (debug/release) — no flavors; the debug/release split
carries the whole dev-vs-prod story (§a2.7).

**Exit criteria:** a0.2 sign-off requested; a0.3–a0.5 recorded here (done by
this document); project skeleton compiles.

## Phase a1 — entry links

### a1.1 Android App Links

Intent filter with `android:autoVerify="true"` for
`https://app.moveo.one/extension/config/*`. Backend/platform team publishes
`https://app.moveo.one/.well-known/assetlinks.json` with the app's
**Play App Signing** SHA-256 fingerprint (plus the upload/debug fingerprints
for internal builds) — the Android counterpart of the AASA file that already
exists for iOS; the two coexist in `.well-known/`. Tapping a setup link with
the app installed opens the app directly; the code takes the exact
fetch → validate → confirm path of a typed code (`SetupLink.kt`).

### a1.2 Custom scheme fallback

`moveoone://config/<code>` — same scheme as iOS, so the landing page's
"Open in app" button is one URL for both platforms. Registered as a second
intent filter; used by QA scripts and by mail clients that wrap https links.

### a1.3 Landing page (extension/platform repo change)

The mobile-aware landing page at `app.moveo.one/extension/config/<code>`
already exists for iOS (App Store badge + code display). Add the Google Play
badge + Play deep link for Android user agents. Owned by the platform repo;
this app only depends on it.

**Exit criteria:** `adb shell am start -a android.intent.action.VIEW -d
"https://app.moveo.one/extension/config/<code>"` opens the app into the
confirmation sheet on a release-signed build; scheme link does the same.
(a2 can proceed in parallel using typed codes + the scheme.)

## Phase a2 — the app

### a2.1 `:studycore` port (Milestone M1)

Port per the map in §0.1. Run `scripts/vendor-tag.sh` first so the fixture
suite and `TagEndpoint.kt` exist. **Acceptance:** every vendored fixture gets
the same verdict (and, for invalids, the same error keys) as the extension
validator; all ported test classes green on JVM.

### a2.2 State machine & screens (M2–M3)

Translate `AppModel.swift` → `AppViewModel.kt` (StateFlow-based, same
`Phase` enum: idle / fetching / failed / studyEnded / consent) and the
screens listed in §0. Copy strings verbatim from the iOS screens (they are
support-vocabulary-aligned with the extension's landing page). Brand tokens
verbatim from `Brand.swift` (near-black on warm neutrals, mono eyebrows,
orange reserved for the live-tracking signal; light-only theme pinned).

Flow invariants to preserve exactly:
- Confirmation sheet (study name, code, origin chips, replacement warning)
  **before** consent; nothing stored, no backend call until Accept.
- Accept → `POST /enroll`; only on success does the study become active
  locally; 409 is success. Network/server enroll failures keep the
  participant on consent with an inline retry message; 410 → studyEnded;
  403 → "study is full".
- Decline ⇒ nothing stored, nothing tracked, no backend call.
- New code while a study is active ⇒ explicit replacement warning; replace
  wholesale on accept.
- Root routing: activeStudy+idle → StudyHome; endedStudy → EndedStudy
  (revoked vs ended wording); else Activation. Deep-link replacement must be
  able to run its confirm→consent flow over an active study.

### a2.3 WebView shell & injection (M4)

`StudyWebView.kt` translating `StudyWebView.swift`:
- One `WebView`, JavaScript + DOM storage enabled, default (persistent)
  cookie store — participants log in once per study, not once per launch.
- On (re)build of the injection state, call `addDocumentStartJavaScript`
  with `ScriptBuilder` output + `allowedOriginRules` from §a0.3. Keep the
  returned `ScriptHandler`s; **re-apply = remove all + add again** (config
  refresh, own-tag yield, target fired, study left) — takes effect from the
  next navigation, mirroring iOS `applyUserScript` and the extension's
  re-registration.
- Bootstrap: `moveo-bootstrap.android.js` = iOS `moveo-bootstrap.ios.js`
  with **only** the `post()` seam changed: `window.moveoNative.postMessage(
  JSON.stringify(msg))` instead of `webkit.messageHandlers.moveo`. Everything
  else (target-match verbatim block, sendEventImmediate/buffer hooks, the
  synthetic `page_view` early-event compensation, own-tag detection & yield,
  per-tab session wipe via sessionStorage flag, `initialized` ping) is copied
  unchanged.
- Multiple windows OFF (`setSupportMultipleWindows(false)`): `target=_blank`
  loads in place — same one-WebView v1 behavior as iOS.
- `onPermissionRequest` → deny (no camera/mic; keeps Data safety clean).
  `DownloadListener` → ignore/deny in v1 (record if a study ever needs it).

### a2.4 JS↔native bridge (M4)

`WebViewCompat.addWebMessageListener(webView, "moveoNative",
allowedOriginRules, listener)` — same origin rules as injection, so the
bridge object doesn't even exist off-study. Message handling ports
`handleBridgeMessage`:
- `{type:"target"}` — event_match target hit (native side is the authority,
  once per study).
- `{type:"ownTag", hostname}` — record in `ownTagHosts`, re-apply the script
  (yield from next load on that host).
- `{type:"initialized", hostname}` — debug-build health surface only.

### a2.5 Navigation policy & URL-driven flow (M4)

`WebViewClient`:
- `shouldOverrideUrlLoading`: non-http(s) schemes (mailto:, tel:, market:,
  bankid:, …) → `ACTION_VIEW` intent to the OS, never a WebView error.
  Main-frame navigations **with a user gesture** (`request.hasGesture()` and
  not `request.isRedirect()`) to an off-origin host → open externally
  (Custom Tab / ACTION_VIEW) and cancel — the WebView must not become a
  general browser. Off-origin **redirect chains** (3-D Secure, PayPal, SSO)
  pass through untracked — blocking them would break the checkout the study
  observes; origin-scoped injection keeps them silent.
- URL-change feed: `doUpdateVisitedHistory` (fires for full loads **and**
  SPA pushState/replaceState — the analogue of the iOS KVO on `webView.url`)
  → `handleBrowserURLChange`: lead-in on the first visit to a tracked origin
  (once per enrollment, skipped after completion), and native `url_match`
  target evaluation via `TargetMatch`.
- System back: `webView.goBack()` when `canGoBack`, else close the browser
  screen (OnBackPressedDispatcher / predictive back).
- Browser chrome mirrors iOS: Done, back, reload, study menu (Leave study;
  debug-only Go-to-URL). No address bar.

### a2.6 Lead surveys, target & lifecycle (M4)

- Lead-in/lead-out open in **Chrome Custom Tabs** (the SFSafariViewController
  analogue: in-app feel, separate cookie store — survey cookies never touch
  the study WebView). Fallback to ACTION_VIEW if no Custom Tabs provider.
- Timing invariants ported verbatim: `leadOutDueAt` persisted **before** the
  2-second delay (app-kill self-heal on next foreground); shown-at flags
  written at presentation, never repeated once shown; a lead-out queued
  behind a visible lead-in gets its turn on dismissal. `appendParticipantId`
  appends the id to the survey URL only when the study opted in. (Android
  adaptation: "presented" = successful Custom Tab launch — the OS gives no
  render callback; recorded in §6.)
- Re-validation (`revalidate()`): on every `ProcessLifecycleOwner` START —
  refresh config; `status == ended` → EndedStudy record + clear active;
  404 → same but `revoked = true` (distinct message); changed config →
  persist + re-apply script; network/server errors → keep the stale-but-
  active study (tracking continues until a *successful* fetch says
  otherwise — extension/iOS posture). Also recovers pending lead-outs.
  Optional: WorkManager periodic (~4h) refresh as bonus, same handler.
- Leave study: confirmation dialog → clear all local study state **and** the
  WebView's site data (cookies, storage, cache) so participant logins do not
  outlive the study. Android adaptation: clear the WebView environment
  wholesale (`CookieManager.removeAllCookies`, `WebStorage.deleteAllData`,
  cache/history) — no per-origin records API like WKWebsiteDataStore, and
  the WebView only ever held study browsing, so wholesale ≥ per-origin
  (recorded in §6).

### a2.7 Debug/release split (M2, ongoing)

The Android analogue of the iOS `#if DEBUG` invariant — **release builds
must not contain the QA surface at all**, hence `src/debug` source sets, not
runtime flags:
- Debug settings screen (gear icon): API-base override (mock/dev/prod),
  effective base display, participant id, event-spy toggle + capture
  export/clear, tag-health ping, vendored-tag provenance.
- Scripted QA hooks: intent extras replace the iOS `MOVEO_*` env vars —
  `adb shell am start … -e MOVEO_API_BASE … -e MOVEO_AUTO_CODE … -e
  MOVEO_AUTO_FLOW consent|enroll|browser -e MOVEO_AUTO_NAV <url>`.
  Debug builds only; release ignores extras.
- Debug ingest redirect (`moveo-ingest-redirect.android.js`, placeholders
  substituted natively) so dev studies' events reach the dev ingestion host;
  debug `ConfigService(enforceTagEndpoint = false)`. Release keeps the
  strict guard and is pinned to prod.
- Debug-only `network_security_config` allowing cleartext to `localhost` /
  `10.0.2.2` (emulator→host loopback) for the mock backend.
- `scripts/mock-backend.sh` — verbatim wrapper around the extension repo's
  `scripts/mock-backend.mjs` (same `--origins`, `/__end`, `/__revive`).

**Exit criteria (a2):** full happy path on emulator against the mock backend
— typed code → confirm → consent → enroll → home → browser opens start URL →
tag initialized ping → url_match target fires → lead-out after 2s → kill
switch via `/__end` deactivates on next foreground → leave clears data.

## Phase a4 — release

### a4.1 Site screening checklist (per study, operational)

Same checklist as iOS: no Google/Facebook-only login wall (WebView
`disallowed_useragent`), site works in a WebView (no extension-dependent
features), checkout redirect chains return to the origin, cookie banners

### a4.2 Play review package

- **Data safety form** (the privacy-labels analogue): app interactions
  collected, linked to a pseudonymous ID, for analytics; no ads, no selling;
  data shared with the study's research team. Mirror the wording basis of
  the iOS privacy labels so the two store declarations tell one story.
- Privacy policy URL (`BackendConstants.privacyPolicyURL` — same open item
  as iOS: confirm final URL first).
- Store listing states plainly that this is a research-participant app that
  tracks interactions on study websites after consent; reviewer notes
  include a working test code against prod (Play reviewers will open the
  app).
- Release hygiene: R8 enabled, no debug source set in the bundle
  (verify: no gear icon, config GETs hit `pigeon.moveo.one` only), Play App
  Signing, versionCode scheme.

### a4.3 Closed-testing pilot (M6/M7)

Physical-device pass first (M6): real study config on prod backend, one real
site end-to-end, LAN-IP mock run for the event spy. Then a closed-testing
track (the TestFlight analogue) with a small real cohort on a pilot study;
watch enroll records, event volume, kill-switch behavior.

### a4.4 Tag update discipline

Tag updates ship **deliberately**: re-run `scripts/vendor-tag.sh` against
the updated extension repo, commit the new `VENDOR.json`
(commit hash + sha256 is the provenance), re-run the fixture suite and the
a3.1 parity diff, then release. Never edit `assets/moveo-one.js`.

**Exit criteria:** production release on Google Play; pilot study data
verified comparable with desktop/iOS cohorts.

## 6. Platform-difference ledger (Android ↔ iOS)

Every deliberate divergence from the iOS reference, in one place:

| Area | iOS | Android | Why |
|---|---|---|---|
| Injection scoping | JS guard + navigation policy (WKUserScript can't filter) | `allowedOriginRules` **+ same JS guard** + navigation policy | platform provides the filter; guard kept as defense in depth |
| Feature availability | OS-versioned APIs | runtime `WebViewFeature` checks; blocking "update WebView" gate | WebView updates independently of the OS |
| Bridge | `WKScriptMessageHandler` (page-global) | `addWebMessageListener` (origin-scoped) | stricter for free |
| Link-tap vs redirect | `navigationType == .linkActivated` | `hasGesture() && !isRedirect()` | closest available signal; both imperfect the same way |
| SPA URL feed | KVO on `webView.url` | `doUpdateVisitedHistory` | equivalent (both catch pushState) |
| Lead surveys | SFSafariViewController sheet; shown-at written after render callback | Custom Tabs; shown-at written at successful launch | Android has no render callback |
| Participant id reinstall survival | Keychain | Auto-Backup-included prefs (best effort) | no keychain analogue; fresh-device-new-participant already accepted |
| Leave-study data clearing | per-origin via WKWebsiteDataStore records | wholesale WebView data clear | no per-origin API; WebView content is study-only, so wholesale ⊇ per-origin |
| Background refresh bonus | BGAppRefreshTask | WorkManager periodic (~4h) | plus: more reliable; still not the mechanism — foreground is |
